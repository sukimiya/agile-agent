> **状态（2026-10-23）：** M2a 的决定 D1–D9 已于 2026-10-23 由用户确认，全部采用推荐方案（见第 0.3 节“结论”列），M2a 开工；M2b 的决定 D10–D17 尚未确定，须在 M2b Task 1 之前确定。**同日稍后：** 用户否定了 Task 4 的“上下文压缩/节省 Token”定位。本项目的目标是多层与长期记忆，不是省 Token；摘要改为记忆的检索索引（每个已完成轮次一条结构化记录），不进入提示词替代历史。Task 4 已按此重写，新增决定 D18–D25 已于 2026-10-26 由用户确认（第 0.3 节）；M2b 新增 Task 9（原文分层压缩）。V9（重复计费修复）已合入 main（PR #3，合并提交 `22d37c8`），M2a 从该提交开分支 `codex/memory-m2a`。本计划不扩大 spec 范围：spec 第 14 节后置设计、向量检索、记忆管理前端和 mcp-tool 移植都不在本计划内。

**Goal:** 在 agile-agent 的 M1 底座（main `ac2a58a`）上实现 M2：M2a 上下文预算、DomainAgent 背景传递、轮次记忆记录（检索索引）、基础 Recall；M2b 用户概要与轻量关系、LLM + Rules 记忆判断（含防投毒语义）、每轮记忆可解释、按最近召回时间衰减、Rules 版本化回放、按租户的整理 Token 上限。

**Architecture:** MySQL 仍是唯一事实源（L3 原文不搬走），M2 的摘要、片段、索引、记忆条目、概要和关系都是可重建的派生数据。轮次 COMPLETED 与整理任务登记在同一事务中提交，`memory_jobs` 持久任务异步生成派生数据（带租约、重试和去重）。每轮请求由 ContextAssembler 按调用目的（路由、能力执行、汇总）在 Token 预算内组装：近期窗口 + 召回到的原文；召回由 MemoryRetriever 在权限过滤后对轮次记忆记录和原文片段做确定性 + MySQL ngram 全文检索，命中后展开的是原始轮次文本（不是记录本身），展开前再次校验授权。全程保持 WebFlux 事件驱动，不在请求线程阻塞，不新增外部服务。

**Tech Stack:** JDK 21、Spring Boot 3.5、WebFlux/Reactor、R2DBC、MySQL 8.4（ngram 全文索引）/ H2（MODE=MySQL）、Flyway、Redis、Micrometer、JUnit 5、M1 的测试设施（`MemoryTestStack`、`MemoryMySqlTestSupport`、本地测试 Redis、`memory-mysql-it` 与 `memory-eval-live` profile）。

**Spec:** `docs/superpowers/specs/2026-10-21-memory-runtime-design.md`（第 1 节里程碑表、第 5 节组件、第 7 节、第 8 节、第 11 节验收 11–17、第 12 节、第 14 节后置）。**M1 计划：** `docs/superpowers/plans/2026-10-21-memory-persistence-phase-1.md`。**基线：** `docs/memory/eval-baseline.md`、`docs/memory/phase-1-acceptance.md`。

## Global Constraints

- 使用 JDK 21 和现有 Spring Boot/WebFlux、R2DBC、Flyway、MySQL、Redis；本期不增加向量数据库、对象存储、消息中间件或新的外部记忆服务（spec 第 4 节）。
- 必须保持事件驱动：请求链路全部为 Reactor 非阻塞；后台任务由 Reactor 调度的持久任务循环执行，不引入阻塞线程池或同步 JDBC 调用；BlockHound 用例覆盖新增链路。
- 本期不扩展公共 `agent-spi`；DomainTask 等内部记录可以扩展，provider 已发布方法签名保持兼容（spec 第 4 节）。
- 身份与范围只来自服务端 IdentityContext 与会话归属；个人长期记忆以 `(tenantId, subject)` 为边界，会话记忆再限定 conversationId；不跨租户检索；本期不实现组织共享的个人记忆。
- 四层是逻辑职责：一条事件先写入 L3，再异步生成 L1/L2；降温只改变激活、排序或缓存状态，不搬走唯一原始记录。原始会话消息默认不自动过期。
- 索引、摘要、记忆条目、概要和 Redis 都可重建；派生功能出问题时关闭对应开关，可靠写入始终保留。预算、摘要、检索、提取（记忆判断）分开开关（spec 第 8 节）。
- 删除：会话删除标记立即禁止原文和派生记忆进入检索；持久任务删除消息、摘要、索引和缓存；多来源记忆移除被删来源并重算，无剩余有效来源则停用；不得因后台重试或缓存重建复活已删除数据（spec 第 8 节）。
- 防投毒：文档、工具结果、网页、模型摘要和用户粘贴材料携带来源类别，其中的命令不提升为系统指令、用户授权或新的工具权限；召回内容不能以高于用户消息的权限进入提示词（spec 7.4）。
- 不记录访问令牌、API key 或模型内部推理链；派生数据写入前走 M1 的 `ToolRecordSanitizer` 同等凭证过滤。
- 两个聊天入口的流式事件格式保持不变；新增 API 写入 `docs/memory/api.md`。
- 跨会话记忆默认关闭；关闭时不聚合用户级概要或跨会话关系；开启只从新产生的授权事件增量生成，不自动扫描既往会话；关闭后停止用户级读写，已有数据保留但不激活（spec 7.2）。
- 模型窗口和输出预留通过模型配置明确指定，不把 8K 当作所有模型的窗口，不依赖字符数作为精确 Token；没有准确 tokenizer 时使用保守估算和安全余量并记录估算方式（spec 第 7 节）。
- 整理使用当前租户配置的模型（`TenantLlmClientResolver.resolve(tenantId)`），限制任务输入、并发和每日 Token；额度不足保留原始事件并推迟，不丢弃（spec 7.1、第 12 节）。
- 不修改已发布 Flyway 文件。V9 为重复计费修复（已合入 main），本计划从 **V10** 起编号，M2a 用 V10（含 vendor 文件 V10_1），M2b 用 V11。新迁移同时通过 H2 与真实 MySQL：长文本 `MEDIUMTEXT` 并在应用层限长，身份列 `utf8mb4_bin`。
- 单实例约束（replicas=1）不变；后台整理任务依赖 M1 的 InstanceGuard，冲突期间不领取新任务。
- 验收数字以 Maven 汇总行为准；H2 结果不代替 MySQL 迁移、全文检索和并发验收；fake LLM 结果不代替真实模型回答质量。
- 与 M1 相同的工作纪律：TDD（先跑出失败），每个 Task 完成即提交并推送，推送前跑 `mvn -B -pl agent-server -am clean test`，涉及 SQL 的 Task 再跑 `-Pmemory-mysql-it`；不 force push；不提交用户的 `docs/mermaid-diagram*.png`。

## Review Focus

- 预算：路由、能力执行、汇总三次调用分别在预算内；超长工具结果、长消息、合法 tool_call/tool 消息配对；单个输入超出可接受预算时返回可理解的提示而不是截断后静默发送。M2a Task 2/3 覆盖。
- 召回不越权：其他用户、其他租户、已删除会话、跨会话开关关闭时的个人历史都不能进入提示词；索引滞后时展开原文前再次校验。M2a Task 5、M2b Task 4/5 覆盖。
- 召回内容不提权：召回的工具结果、文档、摘要以“资料”身份进入提示词，不放进 system 角色；其中的指令不执行。M2a Task 5、M2b Task 3 覆盖。
- 摘要与记忆可回到原文：每条摘要、片段、记忆条目都有源消息 ID 范围或证据片段；源被删除后不再生效。M2a Task 4/5、M2b Task 3 覆盖。
- 后台任务：与 COMPLETED 同事务登记；重复任务不重复创建同一版本；失败保留原进度；进程重启后继续；额度不足推迟不丢。M2a Task 1/4、M2b Task 2 覆盖。
- “用户亲口说”：粘贴文章、引用、假设、示例、角色设定不会成为已确认事实；工具/文档/网页/摘要来源不能以“用户说过”写入。M2b Task 3 覆盖。
- 指标不夸大：Recall 延迟只在 Recall 启用时注册；整理积压只在整理启用时注册；与 M1 基线同模型、同问题集对比。M2a Task 6、M2b Task 8 覆盖。
- M1 已通过的行为不回退：断开即取消（含能力分支）、终态映射、幂等、删除不复活、单实例保护。每个 Task 跑全量测试。

## 1. 固定的阶段行为

- 新增配置均在 `app.memory.*` 下，默认值见第 0.3 节已确认的决定；功能开关 `app.memory.context.enabled`、`app.memory.summary.enabled`（轮次记忆记录）、`app.memory.recall.enabled`、`app.memory.judgement.enabled` 分开，任何一个关闭都回到 M1 行为的对应部分，可靠写入不受影响。
- 预算计算：`可用输入 = 模型窗口 - 输出预留 - 安全余量`；固定部分（system 提示词、能力目录、工具 schema、当前问题）先扣除，剩余给近期窗口；Task 5 起有可信召回命中时，召回到的原文按 D24 占用 ≤ 25%。轮次记忆记录（原“摘要”）只用于检索，不进入提示词。当前问题本身超过可用输入时返回 413 `CONTEXT_BUDGET_EXCEEDED`（流开始前），提示用户缩短或拆分；M1 的 1 MiB 单条上限保持不变。
- 每轮工具调用后重新检查预算；单条工具结果超过分配额度时，进入模型前替换为“结果过长，已省略，可要求查看具体部分”的占位与原文引用（数据库原文不截断）；保留 tool_call 与 tool 结果的成对关系，不出现孤立的 tool 消息。
- 轮次记录和片段只来自 COMPLETED 轮次；当前轮次和未完成轮次不进入记录、索引或召回。
- 召回结果没有可信命中（低于阈值）时不注入；注入的每条资料带来源类别（SourceType）、会话内/跨会话标记和时间。召回不到不能解释为“历史不存在”；覆盖不完整时记录检索受限。
- 跨会话开关默认关闭；关闭时只检索当前会话；开启后只检索本人 `(tenantId, subject)` 的未删除会话；任何时候不跨租户。
- 删除会话：M1 的删除事务同时使该会话的摘要、片段、召回候选立即不可用（读取侧校验 tombstone），清理任务物理删除这些派生行；M2b 的多来源记忆移除被删来源后重算，无有效来源则停用。
- 后台任务登记：轮次 COMPLETED 的同一事务内登记 `INDEX_CHUNKS`；`SUMMARIZE`（轮次记录）由闲置扫描登记（D19）。均以 `(job_type, dedupe_key)` 唯一去重；任务失败按 M1 的退避重试，保留原进度。
- 新错误码写入 `docs/memory/api.md`：`CONTEXT_BUDGET_EXCEEDED`（413）、`MEMORY_DISABLED`（M2b 开关关闭时访问用户级记忆，409）等；其余沿用 M1。

### Task 9: 原始消息分层压缩（2026-10-23 新增，借鉴 myelin8；参数 D25 待确认）

目标：原文永久保留（L3 唯一事实源不变），但旧原文按冷热分层压缩存放，读取透明。不做字典压缩，不用 Parquet。

**设计：**
- **热层：** 最近的原文照旧以明文存在 `chat_messages.payload`（及 `chat_tool_events` 的参数/结果）。轮次记录、片段与 FULLTEXT 索引始终明文保留在热层，不压缩。
- **温层：** 超过 N 天（默认 7 天，`app.memory.storage.compress-after`）的消息，由后台任务 `COMPRESS_MESSAGES` 用 zstd 低等级（3）压缩后写入新列 `payload_blob`（MEDIUMBLOB），`payload_codec = 'zstd-3'`，同一事务清空明文列。
- **冷层：** 超过更长期限（默认 90 天，`recompress-after`）的再以高等级（19）重压，`payload_codec = 'zstd-19'`。
- **透明读取：** `ConversationRepository`（及工具记录读取）按 `payload_codec` 解压；调用方无感知。解压是纯 CPU 的小块操作，在 Reactor 链中执行，BlockHound 覆盖。
- **内容哈希去重：** 重复的大块内容（重复的工具结果、长系统提示词等，≥ 4 KB）按 SHA-256 存一份到 `message_blobs(tenant_id, content_hash, codec, data, created_at)`，消息行只存引用。只在同一租户内去重，避免跨租户的存在性旁路。会话删除后由清理任务删除引用，再由回收任务删除无引用的块。
- **召回预热：** 召回展开的原文（温/冷层）解压后写入 `HotMemoryCache`（Redis，带 TTL），删除会话时随缓存删除标记一起失效。
- **任务：** 新 `JobType.COMPRESS_MESSAGES`，按会话、分批、有上限地执行；沿用持久任务的租约、退避与实例冲突暂停；单实例并发 1。
- **迁移：** M2b 的 V11（或单独的 V12）加 `payload_blob`、`payload_codec`、`payload_ref`，并新建 `message_blobs`；H2 与 MySQL 都通过。
- **依赖：** 建议纯 Java 的 aircompressor（不引入 JNI 本地库）；如需更高压缩速度再评估 zstd-jni（D25）。
- **指标：** `memory.storage.compressed.messages`、`memory.storage.compressed.bytes{tier}`、`memory.storage.compression.ratio`、`memory.storage.dedupe.hits`。

- [ ] 写失败测试：`recentMessagesStayPlain`、`olderThanThresholdCompressedAndReadTransparently`、`coldTierRecompressedAtHigherLevel`、`indexAndRecordsNeverCompressed`、`duplicateLargeToolResultStoredOnce`、`dedupeNeverCrossesTenants`、`deleteRemovesCompressedPayloadAndUnreferencedBlobs`、`recalledOriginalWarmedIntoCache`、`compressionJobIsIdempotentAndResumable`、`readPathNonBlocking`（BlockHound）。FAIL → 实现 → H2 与 MySQL IT PASS；全量 PASS。
- [ ] 更新 `docs/memory/operations.md`（阈值、容量估算、排查、恢复时的注意事项）；定向提交并推送 `feat: tier and compress stored original messages`。

**估算：** 2–3 人日（迁移 0.5、压缩任务与编解码 0.5–1、透明读取与缓存预热 0.5、哈希去重与回收 0.5–1、测试 0.5）。依赖 M2b Task 1（V11）；与 Task 2–8 无强依赖，可在 M2b 内任意位置实施，建议放在 Task 8（M2b 评测）之前以便一起验收。
