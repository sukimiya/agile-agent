## 2. 当前实现与可复用基础

agile-agent 已是 Maven 多模块项目：`agent-spi` 提供身份与能力契约，`agent-server` 提供会话、编排、模型调用和知识能力，`mock-oauth2` 提供开发身份服务。

已核对以下代码（路径相对 `agent-server/src/main/java/io/github/sukimiya/agileagent/`）：

- `service/ChatMemory.java`：使用 `chatmemory:{conversationId}` 保存整段消息 JSON（代码中参数名为 ownerId，实际传入的是会话 ID），无 TTL、无窗口，GET 后 SET 存在并发覆盖风险。
- `agent/Orchestrator.java`：路由和最终回答加载完整历史；最终回答流正常结束后才保存本轮用户和助手消息。能力分支 `answerViaCapabilities`（`:156-171`）把 `dispatcher.dispatch(tasks, llm)` 包成 `.cache()`（`:162`），由 progress 和 results 两个下游共享订阅。已用项目解析到的 reactor-core 3.7.6 实测：下游取消后，被 cache 的上游没有收到 cancel，仍继续发出全部元素；汇总模型调用（`aggregate`，`:173-191`）由于位于 `concatWith(Flux.defer(...))` 之后，不会启动。也就是说，客户端断开后能力执行和工具调用仍会在后台跑完。
- `agent/DomainAgent.java`：能力执行只收到当前问题，缺少必要历史背景。
- `service/SessionService.java`：会话归属检查基于 userId；`touchOrCreate`（`:24-31`）查不到会话 ID 时直接新建。引入长期记忆时必须同时明确租户边界。
- `controller/ChatController.java`：两个聊天入口在请求未携带 conversationId 时都会生成新的会话 ID：OpenAI 兼容入口 `POST /api/chat/completions` 见 `:64`，`POST /api/chat` 见 `:153-155`。`DELETE /api/conversations/{id}`（`:201-203`）当前为空实现。
- `controller/UploadController.java` 与 `service/FileStorageService.java`：附件存于本地磁盘 `${app.upload.dir}/{sanitize(sessionId)}/{name}`：`FileStorageService.sanitize`（`:80-84`）把 `/`、`\` 替换为 `_`，把连续的 `..` 替换为 `_`，因此 `a/b`、`a..b` 与 `a_b` 映射到同一目录（`:73`）；下载则直接用原始 sessionId 拼路径（`UploadController.java:60`）。由于上传可以为任意不存在的 ID 建会话，两个分别授权的会话可能共用一个附件目录。上传（`:77-98`）直接使用请求中的 sessionId，不校验该会话是否属于当前用户；下载（`:46-75`）只检查路径字符，不校验会话或用户归属，任何登录用户凭 sessionId 和文件名即可下载他人文件。上传成功响应的 `Ref(name, path, size)` 返回服务器绝对路径（`FileStorageService.java:20,77`）；IO 失败时 `STORAGE_ERROR` 响应体直接返回 `e.getMessage()`（`UploadController.java:96-97`），可能带出服务器路径。
- `service/UploadCleanupTask.java`：每小时按会话目录修改时间做 24 小时清理，不是按单个文件计时。
- `agent-spi/.../spi/identity/IdentityContext.java`：已有 subject、tenantId、组织范围，记忆权限复用服务端解析的身份。
- 部署：`docker/docker-compose.yml` 的 `agile-agent-server` 服务使用固定 `container_name`，没有声明副本数；`Jenkinsfile` 只构建和推送镜像，不包含部署；仓库内没有 Kubernetes 等编排清单。README 中关于 `LLM_CONFIG_SECRET` 的说明提到“every server instance”，暗示可多实例部署，与本期单实例约束不一致，需在 M1 修正。

相比 mcp-tool，主线已有能力 SPI、通用身份和本地隔离测试设施，因此无需先把企业业务架构搬入 agile-agent。mcp-tool 的角色注册与 SmartLink 继续作为自身适配层。

## 3. 记忆模型

设计参考：[Memory Runtime：从 KV Cache 到长期记忆的分层 AI Memory 架构](https://sukimiya.github.io/blog/memory-runtime.html)。采用关键记忆、目录检索、来源指针和可恢复压缩；具体可靠性与效果需要本项目验收，文章不能替代工程验证。

| 逻辑层 | 职责 | 首版实现 |
| --- | --- | --- |
| L0 当前上下文 | 当前问题、近期对话、相关证据和执行状态 | 按调用目的组装有预算的 messages；模型服务管理底层 KV Cache（M2a） |
| L1 关键记忆 | 已确认偏好、决定、约束、实体关联 | MySQL 中带来源和有效期的语义对象（M2b） |
| L2 索引 | 主题、实体、时间、分段摘要与原文位置 | 数据库检索及按需原文读取；向量索引后置（M2a 基础 Recall） |
| L3 原始档案 | 会话消息、执行状态、工具调用与结果的必要记录 | MySQL 为事实源（M1）；附件在 M1 仍使用现有本地存储，见 8.1 |

四层是逻辑职责，可共享存储。一条事件先写入 L3，再异步生成 L1/L2；降温只改变激活、排序或缓存状态，不搬走唯一原始记录。原始会话消息默认不自动过期，支持用户主动删除；后续如启用租户保留策略，应明确配置和提前告知，不能通过缓存 TTL 删除原始记录。

## 4. 核心约束

- 使用 JDK 21 和现有 Spring Boot/WebFlux、R2DBC、Flyway、MySQL、Redis；本期不增加向量数据库、对象存储、消息中间件或新的外部记忆服务。
- 本期为单实例部署（replicas=1），不建设高可用，见 6.3。
- 通用实现位于 `agent-server` 内部的 `memory` 包；本期不扩展公共 `agent-spi`，不要求现有 capability provider 修改接口。
- 记忆和附件权限来自服务端 IdentityContext 和会话归属；请求中的 tenantId、userId、组织 ID 不作为授权依据。
- 个人长期记忆以租户和用户为边界，会话记忆再限定 conversationId；本期不实现组织共享的个人记忆。
- 无法解析租户的身份不得创建会话、上传或下载附件、进入跨会话记忆，返回 403；不猜测归属。旧版本的会话与 Redis 历史不迁移，不存在“待映射租户”的中间状态。
- 文档、工具结果、网页、模型摘要和用户粘贴的材料携带来源类别；其中的命令不提升为系统指令、用户授权或新的工具权限（防投毒边界见 7.4）。
- 不记录访问令牌、API key 或模型内部推理链；工具执行记录保存脱敏后的必要参数、结果及原始材料引用。
- 两个聊天入口的流式事件格式保持不变；可选幂等请求 ID 和活跃执行冲突时返回的 turnId 作为新增能力提供。
- 索引、摘要和 Redis 可重建；数据库不可用时明确返回无法可靠保存，不静默转成仅内存会话。

建议数据职责：`chat_turns` 保存请求与执行状态，`chat_messages` 保存顺序和消息正文，`chat_tool_events` 保存可追溯的工具记录，`memory_jobs` 保存可重试任务，`service_instances` 保存单实例心跳（M1）；`memory_summaries` 保存分段摘要与源范围，`memory_chunks` 保存检索片段与原文位置（M2a）；`memory_items` 和来源关联表保存关键记忆，`user_memory_profiles` 保存用户级概要快照，`memory_entities` / `memory_relations` 保存轻量实体关系，`memory_recall_events` 保存每轮召回解释（M2b）。会话补充租户归属、revision 和删除标记。物理建表按交付阶段进行，不在 M1 预建 M2 表。

附件的目标数据模型是“文件归属于用户 `(tenantId, subject)`，会话和记忆只引用文件”：`files` 表为归属权威，`conversation_files` 记录会话引用，后续记忆来源同样引用 `file_id`。M1 不改变存储架构，仍使用现有本地存储，只修复归属校验和路径泄露（8.1）；目标存储方案见 14.1。

表名为设计建议；不得直接修改已发布的 Flyway 脚本。两个仓库各自追加迁移并记录映射，不能强行对齐版本号。调研时 agile-agent 已至 V7，mcp-tool 已至 V8，实施前须重新核对。

H2（`MODE=MySQL`）测试与生产共用同一套 Flyway 脚本，新增迁移必须同时在 H2 和真实 MySQL 上执行：消息正文、工具结果等长文本使用 `MEDIUMTEXT`（MySQL `TEXT` 仅 64 KB），并在应用层设置明确上限，超限拒绝而不截断；tenant_id、subject 等身份列使用 `VARCHAR ... COLLATE utf8mb4_bin`（或 `VARBINARY`），保证大小写不同的身份不会被视为同一人。M1 先做 H2 兼容性验证；如个别语法无法兼容（例如 M2a 的 `FULLTEXT ... WITH PARSER ngram`），按 vendor 拆分 Flyway `locations`，不能因此放弃 MySQL 侧约束。

## 6. 写入、恢复与并发

1. 在向客户端提交成功的流式响应之前，验证身份、模型配置及会话归属，成功持久化用户消息并创建执行记录。
2. 每个会话最多一个活跃执行；使用数据库中带租约与版本校验的执行状态防止重复接受。新请求遇到活跃执行时返回 409 `TURN_IN_PROGRESS`，响应体带活跃 `turnId`，前端据此显示“正在生成”；本期不提供按 turnId 重新订阅或续流（后置，见 14.3）。
3. 幂等承诺见 6.4。不提供幂等 ID 的请求视为独立请求，不能仅凭文本相同去重。
4. 工具调用记录采用调用 ID 去重；“已经记录工具调用”不等于外部写操作恰好执行一次。能力工具的业务幂等仍由对应适配器负责。
5. 助手输出按可配置间隔或累计大小保存检查点；初始建议 5 秒或 8 KiB，先达到任一条件即保存。正常结束后提交最终正文。
6. 终态语义与写入方式见 6.2；租约超时的执行经恢复任务标记 INTERRUPTED，过期执行不能覆盖新版本结果。
7. 异常退出可能丢失最后一个成功检查点之后的尾部文本；不承诺每个已显示 Token 都已落库。故障测试记录实际恢复边界。
8. L3 提交和后续整理任务登记在同一数据库事务中完成；后台任务有处理进度、租约和重试，进程重启后可继续。

Redis 缺失、失效、损坏或不可用时从数据库回源；回源失败返回明确错误。缓存 key 加部署命名空间、租户和会话维度，缓存中不保存凭证。

### 6.1 缓存与保留建议值

| 数据 | 建议默认值 | 更新和到期行为 |
| --- | --- | --- |
| MySQL 原始会话消息、有效记忆及来源 | 不自动过期 | 主动删除或显式保留策略生效时处理；业务事实可另有有效期 |
| 本地临时附件（M1） | 24 小时 | 沿用现有清理任务；不承诺长期保留，见 8.1 |
| Redis 近期对话窗口 | 闲置 7 天 | 有效聊天访问续期；仅缓存受大小限制的近期窗口，到期后回源 |
| Redis 用户概要快照（M2b） | 写入后 1 小时 | 概要版本变化时立即失效，读取不延长旧版本寿命；到期后按版本回源 |

TTL 仅用于缓存资源管理，不表示源数据保留期，也不保证 Redis 在 TTL 内不会提前淘汰 key。概要、删除和授权变化要主动失效并校验版本，不能等待 TTL 到期后才停止使用旧数据。首版不缓存通用检索结果，避免过早增加删除和权限失效路径。登录会话的 30 天 TTL 与上述记忆数据分开管理。

### 6.2 M1 终态语义：断开即取消

M1 中客户端断开连接等同于取消：执行的生命周期跟随 SSE 订阅，不存在“客户端断开、后端继续运行”的情况。取消信号沿 Flux 订阅链向上传播，模型流和 `concatMap` 中尚未开始的工具调用都会停止。

| 触发 | 终态 |
| --- | --- |
| 客户端断开连接或取消订阅 | CANCELLED |
| 进程退出，或失去执行权（租约过期、fence 失效） | INTERRUPTED |
| 普通执行失败（模型异常、超时、工具错误、缺少 Completed 等） | FAILED |
| 上游正常结束且收到 Completed | COMPLETED |

- 终态写入使用受管的持久化收尾器（finalizer）：一个被订阅、有超时上限的响应式完成阶段（或专用的 finalizer 组件），负责写入最后检查点和终态，并带 fence 防止覆盖新执行。收尾器失败或超时时，由恢复扫描在租约过期后把执行标记为 INTERRUPTED 作为兜底。
- 禁止在 `doFinally` 中发起不受管理的“fire-and-forget”异步数据库写入。
- 活跃执行的租约已过期时，同会话的新请求在接受事务内先把它标记为 INTERRUPTED（递增 fence），再接受新执行，不必等待恢复扫描；租约未过期仍返回 409 `TURN_IN_PROGRESS`。
- 执行中失去执行权时，流式响应以稳定错误码 `TURN_INTERRUPTED` 的错误事件结束，不发送成功的完成事件。
- 最终回答超过单条消息上限（默认 1 MiB）时记为 FAILED（`MESSAGE_TOO_LARGE`），不保存回答正文，也不截断保存。
- 能力分支必须单独处理：`dispatch(...).cache()` 的共享订阅不会把下游取消传给上游（见第 2 节），M1 须改为由执行持有方显式取消上游（例如去掉 cache、改用 `publish().refCount(...)`/`share()` 等随订阅者归零而取消上游的方式，或持有 dispatch 的 `Disposable` 并在取消时 dispose），保证断开后上游收到 cancel、尚未开始的工具调用不再执行、汇总模型调用不会启动。只测直接回答分支不足以证明断开即取消。
- 已经发出的外部写操作（有副作用的能力工具调用）不能声称已撤销；取消或中断时把这类调用标记为“结果不确定”（UNCERTAIN），不自动重放，在工具记录和前端事件中如实展示。
- 显式取消接口、服务端执行注册表和断开后继续运行的模式为后置设计（14.2、14.3）。

### 6.3 单实例部署与冲突保护

本期只支持单实例：文档和部署配置明确 replicas=1，不建设高可用。

- 检测范围为同一数据库命名空间：每个实例启动时在 `service_instances` 写入心跳行（实例 ID、部署命名空间、启动时间、最近心跳时间），按固定间隔续期；发现同一命名空间内存在其他心跳未过期的实例即视为冲突。
- 检测到冲突时（推荐方案）：输出告警日志和健康检查状态，并拒绝接受新执行（聊天入口返回 503 `INSTANCE_CONFLICT`）；已在运行的执行按正常终态语义收尾。冲突消失后自动恢复接受。
- 如果只选择告警而不拒绝接受，则多实例部署不受支持，取消和终态的可靠性均不承诺；本设计不推荐该选项。
- 多实例与跨实例取消属于后置设计（14.2）。

### 6.4 幂等承诺与上线门槛

- 保证（V9 起）：`Idempotency-Key` 在 `(tenant, subject, key)` 范围内唯一，不依赖 conversationId，保留 24 小时。请求指纹是 SHA-256(入口、客户端给出的 conversationId、消息内容、附件 ID)。
  - 相同 key、相同指纹：已完成则重放，进行中返回 409 `TURN_IN_PROGRESS` 并带 turnId。
  - 相同 key、不同指纹：返回 409 `IDEMPOTENCY_CONFLICT`。
  - 两个入口都在查找 key 之后才生成新的会话 ID，所以未携带 conversationId 的首个请求重试时不会重复执行。
- 未带 key 的请求仍视为独立请求，不凭文本去重。
- 原 M1 只在已建立的会话内生效的限制已由第 13 节的修复取代。

## 7. 上下文与关键记忆

本节为 M2 设计；M1 只提供稳定消息 ID、顺序、原文读取接口和来源类别标注。

上下文预算覆盖系统提示词、能力目录、工具 schema、近期历史、相关原文、工具结果与输出预留。每轮工具调用后重新检查预算，保留工具调用与结果的合法配对；单个输入超过可接受预算时返回可理解的限制提示。

模型窗口及输出预留通过模型配置明确指定；不能把文章示例的 8K 当作所有模型的窗口，也不能依赖字符数作为精确 Token 数。没有准确 tokenizer 时使用保守估算和安全余量，并记录估算方式。

- 路由上下文：当前问题、近期指代、任务背景、能力目录。
- 能力执行上下文（M2a DomainAgent 背景传递）：当前问题、必要近期对话、实体 ID、时间范围、用户约束和经授权检索的证据。
- 汇总上下文：当前问题、必要背景与本次能力结果。

后台轮次记忆记录（原“分段摘要”，2026-10-23 改为检索索引）：会话闲置后为每个已完成轮次生成一条结构化记录（概括、专名、要点、决定标记、关键词、事实/事件类型），保存源轮次与消息 ID 范围、处理到的位置、schema 版本与更新时间。记录只用于检索，不进入提示词替代历史；检索命中后交给模型的是原文。重复任务不重复创建同一版本，失败时保留原进度。

L1 记忆对象包含内容、类型、租户/用户/会话范围、源 ID、来源类别、生成时间、有效期、最近召回时间、状态和替代关系，以及判断所用模型和 Rules 版本。用户亲口确认的信息（定义见 7.4）优先于模型归纳；相互冲突且无法消解的记录保留冲突状态，需要时澄清。业务查询结果附查询时间，需要当前状态时重新调用业务能力。

L2 作为 Memory RAG 检索层，以实体、主题、时间范围、文本相关性检索，限制候选数和总 Token，按需展开原文。先做会话内检索，再由明确的跨会话记忆开关开放个人历史；不跨租户检索。

### 7.1 LLM 负责内容判断，全局 Rules 提供指导（M2b）

由 LLM 判断什么值得保存，以及记住、更新、合并、替代、降低优先级、暂存或忽略；不把“明确偏好/已确认决定”做成仅有两类可保存内容的硬编码白名单。普通但对未来任务有价值的事实、关系和经验同样可由 LLM 选入记忆。

版本化全局 Rules 建议维护在 `agent-server/src/main/resources/memory/global-rules.md`，首版通过代码评审与部署更新，后续再扩展可信管理配置。Rules 指导的重要性因素包括用户亲口表达的偏好、已确认决定、用户强调、重复出现、未来用途、任务约束与时效；要求保留来源、区分事实与推断、避免无证据覆盖和重复保存。

LLM 输出结构化动作、理由、源 ID/证据片段、记忆类型和建议有效期；程序验证格式、来源存在性、权限范围、凭证过滤、删除状态和并发版本。LLM 的重要性/置信分数用于排序，不作为事实已被验证的证明。一般内容选择无需逐条人工确认；证据不足或冲突无法消解时保留候选/冲突状态，不作为已确定事实召回。

全局 Rules 不能被模型自行修改，也不从普通 RAG 文档中加载为高优先级指令。规则变更记录版本，重新整理作为显式可回放任务执行（Rules 版本化回放），不静默批量改写全部历史。

整理任务按租户设置每日 Token 上限和并发上限，使用当前租户配置的模型；额度不足时保留原始事件并推迟整理，不丢弃。

记忆衰减按最近一次被召回的时间计算：长期未被召回的记忆降低排序权重或转为不激活，不删除原始记录；被召回或被用户再次确认时刷新。

### 7.2 用户独立概要和轻量关系图（M2b）

在 `(tenantId, subject)` 下保存独立用户概要、记忆条目、实体与关系。概要是一份有长度预算和处理进度的派生快照，实体/关系以 MySQL 节点和边表表达，首版不引入图数据库或多跳 GraphRAG。

例如“用户偏好中文”“用户负责项目 A”“项目 A 采用方案 B”，分别表示为偏好、用户—项目、项目—决定的有来源记录。每个节点/关系都带范围、有效时间与来源；内容更新保留替代关系，不让旧结论继续作为当前事实生效。召回按当前问题选取相关子图或条目，不把完整用户图谱塞入每轮 Prompt。

跨会话记忆默认关闭。关闭时仅生成和使用当前会话的摘要/记忆，不在后台聚合用户级概要或跨会话关系。用户开启后，从新产生的授权事件增量生成和使用用户级记忆；导入既往会话需要另行显式触发。关闭后停止用户级读写，已存在的概要/图谱保留但不激活；用户可单独删除这些数据。

### 7.3 Memory RAG：索引、Recall 与原文恢复（基础 Recall 属于 M2a）

写入路径为“原始事件落库 → 登记持久任务 → 分段/摘要/LLM 判断 → 建立索引与来源关联”。原始对话分段索引与关键事实索引分开，避免只有被判为重要的信息才能再次找到。片段保留稳定消息范围和邻接关系，索引记录已处理到的消息位置；最近尚未索引的消息由近期窗口覆盖。未索引范围超出近期窗口时，进行有范围上限的原文补检；覆盖不完整则记录检索受限，不能把未召回解释为历史不存在。

读取路径为“解析可信身份与跨会话开关 → 确定可检索范围 → 近期窗口与多路候选召回 → 去重/排序 → 按需展开来源 → 预算内上下文”。索引端过滤租户、用户、会话、删除和有效状态，展开原文前再次验证当前授权；索引滞后不能使已删或已撤权内容重新进入 Prompt。

- 确定性召回：实体 ID、项目名、工单号、日期、时间范围及类型等结构化条件。
- 全文召回：检索原始片段、摘要和关键记忆；中文采用实际 MySQL 支持的 ngram 全文索引并以中文业务语料验证，不以全表 LIKE 代替索引方案。
- 关系召回（M2b）：从命中实体读取受范围约束的一跳关系，限制展开数量，不做无上限图遍历。
- 语义召回：预留 embedding 索引适配器；同义改写等样本召回不足时，再启用向量路径并与全文结果融合。不能假定现有 Redis/MySQL 已安装向量搜索能力。

基础召回与融合尽量使用确定性逻辑。仅对需要的查询按配置启用查询改写或专用重排，避免每轮增加多个 LLM 调用。候选数、关系展开数、最终片段数和输入 Token 都有上限；弱命中不强行注入。向量后端不可用时降级到结构化/全文与近期窗口，返回的内容仍需满足来源和权限约束。

每轮记忆可解释（M2b）：每轮记录实际注入了哪些记忆条目、来自哪些来源、命中原因和排序依据（`memory_recall_events`），用户和开发者可查询“这一轮为什么用了这条记忆”。

RAG 用于选择相关上下文；小规模数据上额外 embedding/重排调用可能使总耗时增加。验收分别测 Recall@K、来源正确率、检索 p50/p95、端到端首字延迟、Token 与索引更新滞后，再决定是否增加向量后端或重排服务。

技术参考：[MySQL ngram 全文解析器](https://dev.mysql.com/doc/refman/8.4/en/fulltext-search-ngram.html)；[全文与向量混合检索概念](https://learn.microsoft.com/en-us/azure/search/hybrid-search-overview)。引用用于说明可选机制，不代表已选用 Azure 或生产数据库版本已确认。

### 7.4 防投毒边界与“用户亲口说”

M1 已具备的基础边界：

- 每条消息、工具结果、检索材料和摘要都标注来源类型（用户输入、助手输出、工具结果、知识库文档、网页、模型摘要等）；
- 按 `(tenantId, subject)` 与会话做租户隔离，跨租户不可见；
- 工具记录和日志的凭证过滤。

M2b 实现的语义判断：

- “用户亲口说”指用户本人明确地表达或确认某项偏好、事实或决定，而不是“消息 role=user”。用户消息中粘贴的文章、转述或引用他人的话、假设（“如果我是……”）、示例、测试用语、要求模型扮演的角色设定，都不会自动成为用户本人的偏好或事实；LLM 在判断时须区分，无法区分时按“候选”保存而不作为已确认事实召回。
- 来源为工具结果、文档、网页或模型摘要的内容，不能以“用户说过”的名义写入记忆，也不能获得指令权限或改写全局 Rules。
- 每条记忆记录判断理由、证据片段和来源类别，配合每轮召回解释（7.3）与 Rules 版本化回放（7.1），使错误或被注入的记忆可以定位、纠正和重算。

## 8. 切换、删除与上线

产品尚未正式部署，新版本不需要旧会话历史：直接切换到新表，旧 Redis `chatmemory:*` key 不读取、不迁移。新代码不再引用 ChatMemory 的整段 JSON 路径，旧 key 由开发环境自行清理，新版本不依赖其是否存在。不设停写迁移窗口，也不提供回退到旧版本的数据兼容。

会话删除先写删除标记，立即禁止原文和派生记忆进入检索，再由持久任务处理消息、摘要、索引和缓存。多来源记忆移除被删来源并重算，无剩余有效来源则停用。不得因后台重试或缓存重建复活已删除数据。

**修订（2026-10-27，用户确定，M2b T5 Q4 重新设计）：** 所有删除改为软删除。会话、执行、消息等数据删除后仍保留在数据库中、可以查询，删除只置 `is_valid = 0`（V13），正常读取、Recall、提示词和用户 API 一律排除无效数据；删除会话只使该会话的内容无效，由它派生的记忆条目停用并标记来源已删除（`source_deleted_at`），不立即删除。召回记录指向条目/索引即计为一次引用；周期任务按“引用数 → 保留期”的可配置分档（默认 0–1 次 1 天、2–4 次 1 周、≥5 次 1 个月，从来源删除时算起）物理清除派生索引行（条目及其来源/关系、片段、轮次记录），原始会话数据与召回记录不物理删除。附件文件同样不再随会话删除而删除。用户可手动减少条目的召回引用数（有审计）。删除审计日志流保留，复放改为置 `is_valid = 0`。

**补充（2026-10-27，用户确认）：** “清除”即分档到期后物理删除派生索引行，原始会话与召回记录永不删除；用户删除（DELETED）与对话中遗忘（FORGOTTEN）的条目永久保留，不参与分档清除。对话中遗忘：只由用户本人当前输入中的“忘记…”指令触发（2026-10-27 下午起：关键词预筛命中后由模型对这条输入做 JSON 模式分类，失败按普通消息；分类 Token 计入该轮 usage 和租户当天记忆额度但不受额度阻止；工具结果、网页、文档不触发），在与 Recall 相同的范围内匹配有效条目（最多 5 条），1 条直接遗忘并告知，多条编号选择（短期令牌，超时或无关回复取消，并在回答开头明确提示“已取消上一次的记忆选择”），0 条不做修改；遗忘把条目置为 FORGOTTEN（仍可在列表查看，不参与 Recall 与概要，可通过 `POST /api/memory/items/{id}/restore` 或“记起来…”恢复），全部写入审计。遗忘后原话不再召回（2026-10-27 下午修订）：指令轮永久排除，FORGOTTEN 条目的来源轮次在遗忘期间排除、恢复后重新可召回；同样的轮次也从同一会话的近期对话窗口中去掉（2026-10-27 傍晚），历史接口仍完整列出。**再补充（2026-10-27，用户决定）：** 召回记录 30 天（可配置）后由周期任务标记过期（只标记、不删除），过期记录不再计入引用数，档位可以下降；删除会话时不删除附件原件（保持现状，只受临时清理约束）。

分开控制预算、摘要、检索与提取功能开关。先启用数据库可靠写入，再开启窗口和摘要，最后开启关键记忆；派生功能出问题时关闭对应开关，可靠写入始终保留。

### 8.1 M1 附件归属修复边界

M1 修复覆盖上传和下载两个方向，保留现有本地存储，不引入新的存储架构：

- 会话 ID 统一规则：两个聊天入口、附件上传/下载和会话删除使用同一个校验规则（例如 `ConversationIds.validate`，只接受小写规范 UUID 字符串），不符合的值直接返回 400，不做任何替换或修剪；附件目录直接使用校验后的原值，任何会被 sanitize 改写的值都被拒绝，从而不存在两个会话映射到同一目录的情况。小写限定同时避免大小写不敏感文件系统上的碰撞。文件名仍按现有规则清理，只影响同一会话目录内的文件。

- 上传：校验 `(tenantId, subject)` 已解析，且请求中的 sessionId 对应的会话属于当前用户；会话尚不存在时，在当前用户名下创建空会话后再写入；会话属于他人、已删除或不存在且无法创建时返回 404。
- 下载：同样校验 `(tenantId, subject)` 与会话归属，再检查路径字符；不匹配统一返回 404，不暴露文件是否存在。
- 去除服务器路径：上传成功响应不再返回 `path`（绝对路径），只返回文件名、大小及用于下载的引用（sessionId + 文件名）；`STORAGE_ERROR` 等错误响应体不再返回 `e.getMessage()`，只返回稳定错误码和通用说明，原始异常只写入服务端日志。拒绝原因（大小、类型不符）保留，但不得包含路径。依赖返回路径拼接消息的前端需改为使用文件名和下载引用。
- 不承诺长期可恢复：由于附件归档已后置（14.1），M1 不承诺附件原件可永久恢复。临时附件仍按现有 24 小时清理任务删除；这与会话消息默认永久保留不同：消息正文和其中提到的文件名会保留，但附件原件可能已被清理。

目标模型（文件归属于用户、会话只引用）和 MinIO 存储见 5 节与 14.1。

## 11. 验收标准

M1：

1. Redis 清空、损坏或不可用后，仍能通过 MySQL 分页读取已提交历史；不同用户和租户不能读到彼此消息。
2. 覆盖正常结束、客户端断开（直接回答分支和能力分支都要测：断开后上游收到 cancel、未开始的工具不执行、汇总模型调用不启动）、超时、模型异常、进程退出、失去 fence 和数据库失败；终态符合 6.2 的映射，最后成功检查点可解释；收尾器失败时由恢复扫描标记 INTERRUPTED；已发出的外部写操作标记为不确定。
3. 同一用户的同一幂等请求不重复入库（V9 起不依赖会话，含未带 conversationId 的首个请求）；不同输入复用同一 ID 返回冲突；同会话并发不覆盖已接受消息；活跃执行冲突返回 409 并带 turnId。
4. 两个聊天入口均回归，现有流式事件格式和 capability provider 契约保持不变。
5. 附件：不符合会话 ID 统一规则的值在所有入口返回 400，`a/b`、`a..b`、`a_b`、大小写变体等不会映射到同一目录；他人或其他租户的上传和下载均返回 404，删除一个会话不会删除其他会话的附件；上传响应和所有错误响应体都不包含服务器路径；临时附件 24 小时清理照常执行，并在 API 说明中写明附件原件不保证永久可恢复。
6. 单实例：部署配置声明 replicas=1；同一数据库命名空间出现第二个活跃实例时产生告警，并拒绝接受新执行。

8. 新版本不读取旧 Redis `chatmemory:*` key；旧 key 存在与否不影响新会话的读写与分页。

## 14. 后置设计（不在本期承诺）

以下内容保留为设计记录，不计入 M1/M2 工作量和验收；启用前需单独确认范围并编写执行计划。

### 14.1 MinIO 存储与附件归档

- 文件归属于用户：MySQL `files` 表为归属权威（服务端生成的 `file_id`、`tenant_id`、`subject`、`bucket`、`object_key`、原文件名、`sha256`、`size`、`content_type`、`status` TEMP/ARCHIVED/DELETE_PENDING/DELETED、时间戳），`conversation_files` 和记忆来源引用 `file_id`。
- bucket 私有，不配置公开或匿名访问策略；object key 为 `{tenantId}/{sha256(subject)}/{fileId}`，原文件名只存在数据库中；接口不返回 bucket、object key 或路径。
- 客户端通过短时效预签名 URL 直连 MinIO（单个对象；例如上传 20 分钟、下载 1 小时，可配置），服务只鉴权和签名，不承担文件 IO；上传后用 `statObject` 核对大小和校验和再确认。
- 批量或分片上传使用 STS AssumeRole，session policy 只允许该对象或该用户前缀上的 Get/PutObject（分片另需 multipart 动作），`DurationSeconds` 例如 1200/3600，MinIO 最小 900 秒。
- TEMP 对象打 `retention=temp` 标签，由 MinIO 按标签的生命周期规则 24 小时过期；被长期记忆引用或用户要求保留时归档：去掉标签（或复制到 archive 前缀并校验 SHA-256），同时把数据库状态改为 ARCHIVED。
- 删除先写数据库删除标记（立即 404、停止签发），再由持久任务删除对象。已签发的凭证无法撤回，删除或撤权最迟在凭证过期时生效，因此有效期保持较短。

### 14.2 独立取消接口、服务端执行注册表与跨实例取消

- `POST /api/turns/{turnId}/cancel`：在取消请求自己的响应式链中校验归属，带 fence 写 CANCEL_REQUESTED，再 dispose 执行，写库成功才返回 200，否则返回错误；前端看到 `CANCEL_REQUESTED → CANCELLED` 的状态事件。
- 服务端执行注册表持有执行（`Disposable` 与可回放 sink），SSE 只是订阅者，显式取消与客户端断开区分处理。
- 多实例时通过 Redis pub/sub 通知持有执行的实例立即停止，租约续期失败作为兜底。

### 14.3 断线重连与续流

- 409 响应中的 turnId 可用于 `GET /api/turns/{turnId}/stream`：先回放数据库检查点，再接上实时输出，不重复启动模型。依赖 14.2 的执行注册表。

### 14.4 长耗时 IO 任务（如媒体转码）的取消

1. 数据库任务状态 CANCEL_REQUESTED 为权威记录；Redis 取消标志和按 taskId 发送的 MQ 消息只用于加速通知。
2. worker 领取排队任务前先检查状态，已取消则跳过。
3. 收到 MQ 消息后立即终止进程（先 SIGTERM，超时后 SIGKILL），定期检查取消标志作为兜底。
4. 取消后清理中间产物；CANCELLED 与 COMPLETED 以先写入数据库的终态为准，由 fence 或版本号防止覆盖。
5. 前端通过 SSE 状态事件看到 `CANCEL_REQUESTED → CANCELLED`，不以点击取消作为成功。
