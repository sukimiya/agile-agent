## 3. 记忆模型

设计参考：[Memory Runtime：从 KV Cache 到长期记忆的分层 AI Memory 架构](https://sukimiya.github.io/blog/memory-runtime.html)。采用关键记忆、目录检索、来源指针和可恢复压缩；具体可靠性与效果需要本项目验收，文章不能替代工程验证。

| 逻辑层 | 职责 | 首版实现 |
| --- | --- | --- |
| L0 当前上下文 | 当前问题、近期对话、相关证据和执行状态 | 按调用目的组装有预算的 messages；模型服务管理底层 KV Cache |
| L1 关键记忆 | 已确认偏好、决定、约束、实体关联 | MySQL 中带来源和有效期的语义对象 |
| L2 索引 | 主题、实体、时间、分段摘要与原文位置 | 数据库检索及按需原文读取；向量索引后置 |
| L3 原始档案 | 会话消息、执行状态、工具调用与结果的必要记录 | MySQL 为事实源；附件字节存放在 MinIO 私有 bucket，归属与状态以 MySQL `files` 表为准 |

四层是逻辑职责，可共享存储。一条事件先写入 L3，再异步生成 L1/L2；降温只改变激活、排序或缓存状态，不搬走唯一原始记录。建议原始会话默认不自动过期，支持用户主动删除；后续如启用租户保留策略，应明确配置和提前告知，不能通过缓存 TTL 删除原始记录。

## 4. 核心约束

- 使用 JDK 21 和现有 Spring Boot/WebFlux、R2DBC、Flyway、MySQL、Redis；附件存储新增 MinIO（S3 兼容 API）。首版不增加向量数据库或新的外部记忆服务；P1 的跨实例取消通知使用 Redis pub/sub，不引入消息中间件。媒体转码等长耗时 IO 任务落地时再按 6.2 节引入 MQ。
- 通用实现位于 `agent-server` 内部的 `memory` 包；首版不扩展公共 `agent-spi`，不要求现有 capability provider 修改接口。
- 记忆权限来自服务端 IdentityContext 和会话归属；请求中的 tenantId、userId、组织 ID 不作为授权依据。
- 个人长期记忆以租户和用户为边界，会话记忆再限定 conversationId；首版不实现组织共享的个人记忆。
- 无法解析租户的身份不得创建会话、上传文件或进入跨会话记忆，返回 403；不猜测归属。旧版本的会话与 Redis 历史不迁移，因此不存在“待映射租户”的中间状态。
- 文档、工具结果、网页与模型摘要携带来源类别；其中的命令不提升为系统指令、用户授权或新的工具权限。
- 不记录访问令牌、API key 或模型内部推理链；工具执行记录保存脱敏后的必要参数、结果及原始材料引用。
- 两个聊天入口和流式事件格式保持不变；可选幂等请求 ID、显式取消和按 turnId 重新订阅作为新增能力提供。附件上传/下载接口按最终设计改为 fileId + 预签名方式，不保留旧的路径式下载接口。
- 索引、摘要和 Redis 可重建；数据库不可用时明确返回无法可靠保存，不静默转成仅内存会话。

## 5. 数据与组件边界

以下是设计层级的组件责任；逐文件接口和迁移编号在各阶段执行计划中确定。

| 单元 | 责任 | 主要集成点 |
| --- | --- | --- |
| ConversationStore | 消息分页、稳定 ID、原始记录和归属验证 | ChatController、SessionService、ChatMemory |
| TurnLifecycle | 请求幂等、同会话执行互斥、状态转换、检查点和异常恢复 | Orchestrator、TaskDispatcher、DomainAgent |
| TurnRegistry | 本实例持有的运行中执行（`Disposable` 与可重放的输出 sink），处理取消通知和按 turnId 重新订阅 | TurnLifecycle、ChatController、Redis pub/sub |
| FileStore | `files` 归属记录、MinIO 对象 key、预签名 URL/STS 签发、上传确认、生命周期标签、删除任务 | UploadController、记忆来源引用、MinIO |
| HotMemoryCache | 近期消息缓存、版本校验、失效与数据库回源 | 替换 ChatMemory 的整段 JSON 写入路径 |
| ContextAssembler | 为路由、能力执行、汇总分别组装预算内上下文 | Orchestrator、内部 DomainTask、DomainAgent |
| ConsolidationWorker | 分段摘要、LLM 记忆判断、概要/关系更新、冲突与过期处理 | 持久任务队列、版本化 Rules 与源记录 |
| MemoryIndex | 原始片段、摘要、事实和实体关系的可重建检索索引 | MySQL 索引；可选向量索引适配器 |
| MemoryRetriever | 权限过滤、多路召回、去重、排序、来源展开 | MemoryIndex、ContextAssembler、受控原文读取 |

建议数据职责：`chat_turns` 保存请求与执行状态，`chat_messages` 保存顺序和消息正文，`chat_tool_events` 保存可追溯的工具记录，`memory_summaries` 保存分段摘要与源范围，`memory_items` 和来源关联表保存关键记忆，`memory_jobs` 保存可重试整理任务。增加 `user_memory_profiles` 保存用户级概要快照，`memory_entities` / `memory_relations` 保存轻量实体关系，`memory_chunks` 保存检索片段与原文位置。会话补充租户归属、revision 和删除标记。附件使用 `files`（归属权威）和 `conversation_files`（会话引用）两张表，后续长期记忆的来源引用同样指向 `file_id`。物理建表按交付阶段进行，不在 P1 预建全部 P3 表。

表名为设计建议；不得直接修改已发布的 Flyway 脚本。两个仓库各自追加迁移并记录映射，不能强行对齐版本号。调研时 agile-agent 已至 V7，mcp-tool 已至 V8，实施前须重新核对。

H2（`MODE=MySQL`）测试与生产共用同一套 Flyway 脚本，新增迁移必须同时在 H2 和真实 MySQL 上执行：消息正文、工具结果等长文本使用 `MEDIUMTEXT`（MySQL `TEXT` 仅 64 KB），并在应用层设置明确上限，超限拒绝而不截断；tenant_id、subject 等身份列使用 `VARCHAR ... COLLATE utf8mb4_bin`（或 `VARBINARY`），保证大小写不同的身份不会被视为同一人。Task 1 先做 H2 兼容性验证；如个别语法无法兼容（例如 P3 的 `FULLTEXT ... WITH PARSER ngram`），按 vendor 拆分 Flyway `locations`，不能因此放弃 MySQL 侧约束。

## 6. 写入、恢复与并发

1. 在向客户端提交成功的流式响应之前，验证身份、模型配置及会话归属，成功持久化用户消息并创建执行记录。
2. 每个会话最多一个活跃执行；使用数据库中带租约与版本校验的执行状态防止多实例重复接受。新请求遇到活跃执行时返回 409，响应体带上活跃 `turnId`；客户端刷新或断网重连时通过 turnId 重新订阅正在运行的输出流（见 6.2），或显式取消后再发起新请求，不需要等待租约过期。
3. 同一幂等 ID、相同输入不重复创建消息或执行；同一 ID、不同输入返回冲突。不提供幂等 ID 的请求视为独立请求，不能仅凭文本相同去重。
4. 工具调用记录采用调用 ID 去重；“已经记录工具调用”不等于外部写操作恰好执行一次。能力工具的业务幂等仍由对应适配器负责。
5. 助手输出按可配置间隔或累计大小保存检查点；初始建议 5 秒或 8 KiB，先达到任一条件即保存。正常结束后提交最终正文。
6. 保存 COMPLETED、FAILED、CANCEL_REQUESTED、CANCELLED、INTERRUPTED 状态；租约超时的执行经恢复任务标记中断，过期执行不能覆盖新版本结果。
7. 异常退出可能丢失最后一个成功检查点之后的尾部文本；不承诺每个已显示 Token 都已落库。故障测试记录实际恢复边界。
8. L3 提交和整理任务登记在同一数据库事务中完成；后台任务有处理进度、租约和重试，进程重启后可继续。

Redis 缺失、失效、损坏或不可用时从数据库回源；回源失败返回明确错误。缓存 key 加部署命名空间、租户和会话维度，缓存中不保存凭证。

### 6.1 缓存与保留建议值

| 数据 | 建议默认值 | 更新和到期行为 |
| --- | --- | --- |
| MySQL 原始会话、有效记忆及来源 | 不自动过期 | 主动删除或显式保留策略生效时处理；业务事实可另有有效期 |
| Redis 近期对话窗口 | 闲置 7 天 | 有效聊天访问续期；仅缓存受大小限制的近期窗口，到期后回源 |
| Redis 用户概要快照 | 写入后 1 小时 | 概要版本变化时立即失效，读取不延长旧版本寿命；到期后按版本回源 |

TTL 仅用于缓存资源管理，不表示源数据保留期，也不保证 Redis 在 TTL 内不会提前淘汰 key。概要、删除和授权变化要主动失效并校验版本，不能等待 TTL 到期后才停止使用旧数据。首版不缓存通用检索结果，避免过早增加删除和权限失效路径。登录会话的 30 天 TTL 与上述记忆数据分开管理。

### 6.2 事件驱动的取消与重新订阅

Web 端保持事件驱动：用户的取消请求到达服务器时立即执行；无法执行时前端得到失败响应，而不是先显示成功。

- 执行由服务端持有。每个运行中的 turn 登记在本实例的 TurnRegistry 中（保存执行的 `Disposable` 和带回放能力的输出 sink），SSE 连接只是这个执行的一个订阅者。客户端断开连接只是取消订阅，不等于取消执行；执行继续按检查点落库，结束后写入终态。
- 显式取消接口为 `POST /api/turns/{turnId}/cancel`。取消请求在自己的响应式链中先校验 turn 归属（不匹配返回 404），再带 fence 在数据库中把状态写为 CANCEL_REQUESTED，然后 dispose 执行；Flux 的取消信号沿订阅链向上传播，模型流和 `concatMap` 中尚未开始的工具调用都会停止。执行停止后写入 CANCELLED（保留最后检查点的部分文本）。数据库写入成功后才返回 200；turn 已是终态返回 409 `TURN_TERMINATED`，写库失败返回 503。所有写库都挂在被订阅的取消请求链上，不依赖 `doFinally` 中未受管理的异步写入。
- 多实例部署时取消请求可能落在其他实例。该实例写库后通过 Redis pub/sub（频道含部署命名空间与 turnId）通知持有执行的实例立即 dispose；通知丢失时，持有方在下一次租约续期（15 秒）读到 CANCEL_REQUESTED 或失去 fence 后停止，作为兜底。
- 重新订阅：`GET /api/turns/{turnId}/stream` 在归属校验后，从数据库检查点回放已保存文本，再接上本实例 sink 的实时输出；执行不在本实例时，按检查点轮询数据库直到终态。同一 turn 不会因为重新订阅而第二次启动模型。
- 已经发出的有副作用的外部工具调用无法撤回：取消时标记为“结果不确定”（UNCERTAIN），不自动重放，在工具记录和前端事件中如实展示。
- 前端通过 SSE 事件看到 `CANCEL_REQUESTED → CANCELLED` 的状态变化，不在点击取消时直接显示成功。

长耗时 IO 任务（例如媒体转码）采用同一原则，在相应功能落地时实现：

1. 数据库中的任务状态 CANCEL_REQUESTED 是权威记录；Redis 中的取消标志和按 taskId 发送的 MQ 取消消息只用于加速通知，防止 Redis 丢 key 或 MQ 丢消息后取消失效。
2. worker 领取排队中的任务前先检查数据库状态，已是 CANCEL_REQUESTED 则直接跳过并写 CANCELLED。
3. worker 收到 MQ 取消消息后立即终止当前进程（先 SIGTERM，超时后 SIGKILL），不等待下一次轮询；执行过程中定期检查取消标志作为兜底。
4. 取消后清理已产出的中间文件或分片，再写终态 CANCELLED；如果转码在取消前刚好完成，以先写入数据库的终态（COMPLETED 或 CANCELLED）为准，由 fence 或版本号防止互相覆盖。
5. 前端通过 SSE 状态事件看到 `CANCEL_REQUESTED → CANCELLED`（或 COMPLETED），不以点击取消作为成功。

## 7. 上下文与关键记忆

上下文预算覆盖系统提示词、能力目录、工具 schema、近期历史、相关原文、工具结果与输出预留。每轮工具调用后重新检查预算，保留工具调用与结果的合法配对；单个输入超过可接受预算时返回可理解的限制提示。

模型窗口及输出预留通过模型配置明确指定；不能把文章示例的 8K 当作所有模型的窗口，也不能依赖字符数作为精确 Token 数。没有准确 tokenizer 时使用保守估算和安全余量，并记录估算方式。

- 路由上下文：当前问题、近期指代、任务背景、能力目录。
- 能力执行上下文：当前问题、必要近期对话、实体 ID、时间范围、用户约束和经授权检索的证据。
- 汇总上下文：当前问题、必要背景与本次能力结果。

后台分段摘要保存源消息 ID 范围、处理到的位置、生成版本与更新时间。摘要不能替代原文；重复任务不重复创建同一版本，失败时保留原进度。

L1 记忆对象包含内容、类型、租户/用户/会话范围、源 ID、生成时间、有效期、状态和替代关系，以及判断所用模型和 Rules 版本。用户明确确认的信息优先于模型归纳；相互冲突且无法消解的记录保留冲突状态，需要时澄清。业务查询结果附查询时间，需要当前状态时重新调用业务能力。

L2 作为 Memory RAG 检索层，以实体、主题、时间范围、文本相关性检索，限制候选数和总 Token，按需展开原文。先做会话内检索，再由明确的跨会话记忆开关开放个人历史；不跨租户检索。

### 7.1 LLM 负责内容判断，全局 Rules 提供指导

由 LLM 判断什么值得保存，以及记住、更新、合并、替代、降低优先级、暂存或忽略；不把“明确偏好/已确认决定”做成仅有两类可保存内容的硬编码白名单。普通但对未来任务有价值的事实、关系和经验同样可由 LLM 选入记忆。

版本化全局 Rules 建议维护在 `agent-server/src/main/resources/memory/global-rules.md`，首版通过代码评审与部署更新，后续再扩展可信管理配置。Rules 指导的重要性因素包括明确偏好、已确认决定、用户强调、重复出现、未来用途、任务约束与时效；要求保留来源、区分事实与推断、避免无证据覆盖和重复保存。

LLM 输出结构化动作、理由、源 ID/证据片段、记忆类型和建议有效期；程序验证格式、来源存在性、权限范围、凭证过滤、删除状态和并发版本。LLM 的重要性/置信分数用于排序，不作为事实已被验证的证明。一般内容选择无需逐条人工确认；证据不足或冲突无法消解时保留候选/冲突状态，不作为已确定事实召回。

全局 Rules 不能被模型自行修改，也不从普通 RAG 文档中加载为高优先级指令。规则变更记录版本，重新整理作为显式可回放任务执行，不静默批量改写全部历史。

### 7.2 用户独立概要和轻量关系图

在 `(tenantId, subject)` 下保存独立用户概要、记忆条目、实体与关系。概要是一份有长度预算和处理进度的派生快照，实体/关系以 MySQL 节点和边表表达，首版不引入图数据库或多跳 GraphRAG。

例如“用户偏好中文”“用户负责项目 A”“项目 A 采用方案 B”，分别表示为偏好、用户—项目、项目—决定的有来源记录。每个节点/关系都带范围、有效时间与来源；内容更新保留替代关系，不让旧结论继续作为当前事实生效。召回按当前问题选取相关子图或条目，不把完整用户图谱塞入每轮 Prompt。

跨会话记忆默认关闭。关闭时仅生成和使用当前会话的摘要/记忆，不在后台聚合用户级概要或跨会话关系。用户开启后，从新产生的授权事件增量生成和使用用户级记忆；导入既往会话需要另行显式触发。关闭后停止用户级读写，已存在的概要/图谱保留但不激活；用户可单独删除这些数据。

### 7.3 Memory RAG：索引、Recall 与原文恢复

写入路径为“原始事件落库 → 登记持久任务 → 分段/摘要/LLM 判断 → 建立索引与来源关联”。原始对话分段索引与关键事实索引分开，避免只有被判为重要的信息才能再次找到。片段保留稳定消息范围和邻接关系，索引记录已处理到的消息位置；最近尚未索引的消息由近期窗口覆盖。未索引范围超出近期窗口时，进行有范围上限的原文补检；覆盖不完整则记录检索受限，不能把未召回解释为历史不存在。

读取路径为“解析可信身份与跨会话开关 → 确定可检索范围 → 近期窗口与多路候选召回 → 去重/排序 → 按需展开来源 → 预算内上下文”。索引端过滤租户、用户、会话、删除和有效状态，展开原文前再次验证当前授权；索引滞后不能使已删或已撤权内容重新进入 Prompt。

- 确定性召回：实体 ID、项目名、工单号、日期、时间范围及类型等结构化条件。
- 全文召回：检索原始片段、摘要和关键记忆；中文采用实际 MySQL 支持的 ngram 全文索引并以中文业务语料验证，不以全表 LIKE 代替索引方案。
- 关系召回：从命中实体读取受范围约束的一跳关系，限制展开数量，不做无上限图遍历。
- 语义召回：预留 embedding 索引适配器；同义改写等样本召回不足时，再启用向量路径并与全文结果融合。不能假定现有 Redis/MySQL 已安装向量搜索能力。

基础召回与融合尽量使用确定性逻辑。仅对需要的查询按配置启用查询改写或专用重排，避免每轮增加多个 LLM 调用。候选数、关系展开数、最终片段数和输入 Token 都有上限；弱命中不强行注入。向量后端不可用时降级到结构化/全文与近期窗口，返回的内容仍需满足来源和权限约束。

RAG 用于选择相关上下文；小规模数据上额外 embedding/重排调用可能使总耗时增加。验收分别测 Recall@K、来源正确率、检索 p50/p95、端到端首字延迟、Token 与索引更新滞后，再决定是否增加向量后端或重排服务。

技术参考：[MySQL ngram 全文解析器](https://dev.mysql.com/doc/refman/8.4/en/fulltext-search-ngram.html)；[全文与向量混合检索概念](https://learn.microsoft.com/en-us/azure/search/hybrid-search-overview)。引用用于说明可选机制，不代表已选用 Azure 或生产数据库版本已确认。

## 8. 切换、删除与上线

产品尚未正式部署，新版本不需要旧会话历史：直接切换到新表，旧 Redis `chatmemory:*` key 不读取、不迁移，旧的本地上传文件也不导入 MinIO。新代码不再引用 ChatMemory 的整段 JSON 路径，旧 key 由开发环境自行清理，新版本不依赖其是否存在。不设停写迁移窗口，也不提供回退到旧版本的数据兼容。

会话删除先写删除标记，立即禁止原文和派生记忆进入检索，再由持久任务删除消息、摘要、索引和缓存。多来源记忆移除被删来源并重算，无剩余有效来源则停用。不得因后台重试或缓存重建复活已删除数据。文件删除规则见 8.1。

分开控制预算、摘要、检索与提取功能开关。先启用数据库可靠写入，再开启窗口和摘要，最后开启关键记忆；派生功能出问题时关闭对应开关，可靠写入始终保留。

### 8.1 附件：用户归属与 MinIO

文件归属于用户，不归属于会话；会话和记忆只引用文件。

- 归属权威：MySQL `files` 表，字段包括服务端生成的 `file_id`（UUID）、`tenant_id`、`subject`、`bucket`、`object_key`、原文件名、`sha256`、`size`、`content_type`、`status`（TEMP / ARCHIVED / DELETE_PENDING / DELETED）、`created_at`、`confirmed_at`、`archived_at`、`deleted_at`。`tenant_id` 和 `subject` 只取自服务端 IdentityContext，不信任请求中的值。`conversation_files(conversation_id, file_id, source_type, source_id)` 记录会话引用，P3 的记忆来源引用同样指向 `file_id`，一个文件可被多个会话或多条记忆引用。
- 存储：bucket 私有，不配置任何公开或匿名访问策略。object key 为 `{tenantId}/{sha256(subject)}/{fileId}`，不包含用户提供的文件名；原文件名只保存在数据库中。接口不返回 bucket、object key 或任何服务器路径，只返回 `fileId`。
- 客户端直连 MinIO：服务只负责鉴权、写归属记录和签名，文件字节不经过服务，避免服务承担文件 IO。
  - 单文件上传/下载使用预签名 URL，每个 URL 只对应一个对象；建议默认上传 20 分钟、下载 1 小时，可配置。
  - 批量或分片上传使用 STS AssumeRole 签发临时凭证，附带 session policy，只允许 `s3:PutObject` / `s3:GetObject`（分片上传另需相应的 multipart 动作）作用于该对象或该用户前缀；`DurationSeconds` 建议上传 1200、下载 3600，MinIO 最小值为 900 秒。
- 上传流程：服务校验身份并写入 `files`（TEMP）→ 签发预签名 PUT 或 STS → 客户端直传 MinIO → 客户端调用确认接口，服务用 `statObject` 核对大小和校验和（以及类型、大小上限）后记录 `confirmed_at`；核对失败则删除对象并标记失败。未确认的对象不能被会话或记忆引用。
- 下载流程：`GET /api/files/{fileId}`（或 `/api/files/{fileId}/download-url`）查询 `files`，要求 `tenant_id`、`subject` 与当前身份一致且状态有效，然后签发预签名 GET。不匹配、已删除或不存在统一返回 404，不暴露文件是否存在。
- 24 小时临时清理：TEMP 对象上传时打 `retention=temp` 标签，由 MinIO 按标签的生命周期规则在 24 小时后过期，取代按目录修改时间扫描的清理任务。被长期记忆引用或用户明确要求保留时归档：去掉该标签（或服务端复制到 archive 前缀并校验 SHA-256），并在同一数据库事务中把状态改为 ARCHIVED；归档完成前不能建立长期来源关系。
- 删除：先在数据库中写删除标记（DELETE_PENDING），从这一刻起所有读取返回 404、停止签发新的 URL 或凭证，再由持久任务删除 MinIO 对象并改为 DELETED；重试和缓存重建不能使文件复活。移除单个来源引用不删除仍被引用的文件；用户明确删除文件时，先使文件及其全部引用不可用，再异步清理。
- 限制：已签发的预签名 URL 和 STS 凭证无法撤回，删除或撤权最迟在凭证过期时才完全生效，因此有效期保持较短，并在 API 说明中写明。

## 11. 验收标准

1. Redis 清空、损坏或不可用后，仍能通过 MySQL 分页读取已提交历史；不同用户和租户不能读到彼此消息。
2. 覆盖正常结束、显式取消、客户端断开、超时、模型异常、进程退出和数据库失败；执行状态与最后成功检查点可解释。显式取消只有在 CANCEL_REQUESTED 写库成功后才返回 200，跨实例取消可立即生效；断开后可按 turnId 重新订阅，不会被锁到租约过期。
3. 同一幂等请求不重复入库；不同输入复用同一 ID 返回冲突；同会话并发不覆盖已接受消息。
4. 两个聊天入口均回归，现有流式事件格式和 capability provider 契约保持不变。
5. 逐轮验证上下文预算，覆盖超长工具结果、长消息和合法工具消息配对。
6. 使用中立 fixture 验证指代追问、早期细节召回、冲突修正、跨会话开关及来源恢复；资料中的命令不能取得更高指令权限。
7. 删除后，原文、派生记忆和缓存均不能再被召回或后台重建复活。
8. 新版本不读取旧 Redis `chatmemory:*` key；旧 key 存在与否不影响新会话的读写与分页。
9. 在同模型、同问题集上比较关键事实召回、来源正确率、错误记忆、输入 Token、首字延迟与检索延迟。先建立基线再锁定质量门槛，不预先承诺固定节省比例。
10. 主线测试与 mcp-tool 适配测试分别记录，不能用一仓结果代替另一仓结果。
11. 跨会话开关默认关闭；关闭时不聚合用户级概要，开启不自动扫描全部既往会话，关闭后停止用户级读写，删除不会被后台任务复活。
12. LLM 可依据 Rules 保存明确偏好以外的有价值记忆；无效来源、越权、已删材料和格式错误不能提交。规则版本及判断理由可追溯，检索材料不能改写全局 Rules。
13. 使用可控时间验证近期窗口闲置 7 天与概要 1 小时的缓存建议值，以及概要更新/删除/撤权后的主动失效和数据库回源。
14. 中文全文、实体精确匹配、关系展开和语义改写分别评测；基础 RAG 不依赖向量服务才能工作，索引滞后不丢失近期背景。
15. 附件归属于 `(tenantId, subject)`：其他用户或租户的上传确认、下载、归档和删除均返回 404；接口不返回 bucket、object key 或服务器路径；bucket 无公开策略。预签名 URL/STS 只作用于单个对象或该用户前缀并按配置过期；TEMP 对象由标签生命周期 24 小时过期，ARCHIVED 对象不受影响；删除后立即 404 且不再签发凭证。
16. 生产恢复目标为 RPO ≤ 15 分钟、RTO ≤ 4 小时；只有数据库、MinIO 附件、密钥依赖和删除清单的恢复演练通过后才能宣称达标。

主线验证从仓库根目录使用 `mvn -pl agent-server -am test`、`mvn -pl agent-spi -am test` 和相应打包命令；需用 JDK 21（任意发行版，基线已在 Linux 上用 OpenJDK 21.0.12 验证），并准备隔离的本地 Redis、MinIO 与真实 MySQL 集成环境。H2 用于快速测试，不替代 MySQL 迁移和并发行为验证。下游使用其自身 Maven 测试与企业适配环境。

用户于 2026-10-21 确认推荐方案：原始会话默认不自动过期；跨会话记忆默认关闭；LLM 在全局 Rules 指导下选择长期记忆；被长期记忆引用或用户明确要求保留的附件归档，其他临时附件沿用 24 小时清理；生产以 RPO ≤ 15 分钟、RTO ≤ 4 小时为待验证目标。

- 附件：使用服务端文件 ID、内容校验和及来源关联；归档在数据库事务中完成状态变更后才建立长期来源关系。长期证据只引用 `file_id` 和校验和，不引用 object key、预签名 URL 或任何路径。
- 模型与成本：P2/P3 的整理使用当前租户配置的模型，独立限制任务输入、并发和每日 Token 预算；预算不足保留原始事件并推迟整理。具体额度在各阶段配置与评测中确定，不在 P1 启用后台 LLM 整理。
- Recall：P2/P3 执行计划确定分块、候选数量和阈值，通过固定回归集调整；没有可信命中时不注入猜测。P1 提供稳定消息 ID、顺序和原文读取接口。
- 用户控制：P1 完成会话与附件的用户归属、读取、取消和删除；P3 增加个人记忆开关、查看、更正、删除和来源解释 API，复杂管理 UI 后置。
- 恢复：生产开服前验证离开数据库故障域的备份与日志；恢复到指定时间点后复放删除清单，再重建缓存/索引。删除清单不完整时，不开放无法核实的范围。恢复目标是验收条件，不是对尚未配置的基础设施的保证。
- 计划拆分：本阶段执行计划仅覆盖 P0/P1；P2 上下文预算和 P3 Memory RAG/用户记忆分别形成后续计划，保持公共 SPI 兼容。

## 13. 已知问题与后续版本

- 重复执行/重复计费：计划中的 `Idempotency-Key` 按会话范围去重，但 OpenAI 兼容入口 `POST /api/chat/completions` 在请求未携带 `conversationId` 时每次都生成新会话 ID（`ChatController.java:63-64`），客户端带同一个 key 重试也会被当作新请求，导致重复执行、重复调用模型和重复计费。本版本记录该问题，不在 P1 修复；在下一版本中解决，详见 main 分支 `docs/known-issues/2026-10-21-idempotency-duplicate-billing.md`。

本文件及后续修订均为设计成果；尚未实施记忆功能或完成新功能回归。2026-10-21 已运行现有代码的 32 项定向基线测试并通过，命令和结果记录在 P0/P1 执行计划中，不能作为新功能或生产恢复能力的验证结论。
