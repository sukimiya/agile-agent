# autoDream：模型自己整理索引、关键记忆和概要

> **状态：autoDream 是作者正在考虑的核心方向，不是已批准的实现规格，没有排期，也没有承诺现有代码已经这样做。**

agile-agent 要服务下面两篇文稿的目标。本次依据的是作者**上传的 HTML 文稿**，不是从公网重新抓取的页面，因此这里不附文章网址，也不把文中的测量写成本仓库已经复现的基准。

- 《Memory Runtime：从 KV Cache 到长期记忆的分层 AI Memory 架构》
- 《Temporal Semantic Runtime v2.0 — A Dual-Path Cognitive Runtime for Embodied Agents》

第一篇把长期记忆从「无限变长的上下文」里拆出来：正在用的热上下文要有预算，重要的事可以记成带来源指针的语义对象，目录负责导航，原始档案保留发生过的事。压缩减少的是正在使用的上下文，不是把档案本身切掉。第二篇把快速反应和慢速思考分成同时存在的路径：世界可以很大，送进模型的上下文应当稀疏；思考不应挡住仍需立刻完成的反应。记忆的积累本身就是一种学习，不必靠不断改模型参数。

autoDream 是把这两点收成 agile-agent 自己的整理方式：模型回头看已经有过的经历，自己决定要不要整理、何时整理、怎样改索引、关键记忆和概要，以及这些结果以后怎样进入回答。调度只提供动手的机会，不规定这一次必须改哪一条。

## 普通一轮对话不是整理

前台的一轮是在组装这条消息并回答。它会读最近对话、按需召回，也可能在消息里引用概要的一部分。用过记忆，还不等于整理过记忆。

整理发生在回答路径之外。模型面对的是已经留下的经历和现有的索引、关键记忆、概要，然后决定它们以后长什么样。决定「这次什么都不用改」同样是一次完整的整理。

## 模型自己走完这一轮

一次 autoDream 大致是：

1. 运行时交出材料和一次动手的机会：原始经历、已经有的索引、关键记忆和概要，以及读写这些派生结果的途径。它不附带「必须合并这些、必须删那些」的脚本。
2. 模型自己看这些经历。可以改索引，可以提升或改写关键记忆，可以重写概要，也可以判定眼下没有值得动的地方。
3. 改动留在派生结果里。之后的召回和回答使用这些结果，而不是把同一次整理塞进正在进行的那条回复。
4. 后来的对话又变成新的经历。下一次机会到来时，模型再看，包括看自己上次的整理是否还站得住。

何时给予机会可以由配置打开。本文不规定钟点，也不要求每个周期把全部历史重扫一遍。机会不等于任务清单。

前台组装消息和后台这次整理是两条路径。若以后有独立的安全路径或实时反应路径，整理同样不插进去。这是为了让慢的思考不挡住仍要立刻完成的事，不是为了给库存记忆规定容量。

## 存下来的记忆，和这一条消息里引用的概要

资源紧，约束的是**正在进行的处理**和**这一条消息里放进提示词的选择**，不是库存记忆必须被裁短。

存下来的记忆可以保持完整。存下来的概要也可以保持模型已经写成的全文。某一次请求的上下文短，只影响**这一条消息引用概要时选出的那一段有多长**。这段选择随两件事一起伸缩：配置里的上下文长度，以及当前部署环境（模型若在本机，热上下文更吃紧；若走远程 API，更直接影响的是这条消息的输入规模、费用和延迟）。本文不规定固定比例。选出的那一段由模型自己决定写哪些意思、用什么表示；它不是一份用来覆盖库存概要的截断副本。

本地部署所以要省着处理，是因为机器有限，不是因为记忆条数或概要全文必须设顶。几种开销不能互相代替：

| 预算 | 指什么 | 和当前服务端的关系 |
| --- | --- | --- |
| 进程内存 | JVM 堆、直接内存、本进程的缓存 | 镜像默认把堆设为 1 GB（`-Xms256m` / `-Xmx1024m`），这是镜像参数，不是测出来的最低内存 |
| 模型常驻与 KV | 模型权重，以及随上下文变长的 Key/Value 缓存 | 现有对话走租户配置的远程 API。提供方的 KV 不在本进程里，服务端改提示词长度，并不直接缩小提供方机器上的 KV |
| 输入 token 预算 | 这一轮真正放进提示词的窗口 | 已有按模型窗口估算的上下文预算，默认开启。它约束的是这一条消息，不是库存 |
| 磁盘档案 | 库里的原文、派生索引、附件文件 | MySQL 保存会话与派生数据；附件在本地目录，另有按修改时间清理的任务 |

只有模型跑在本机时，缩短这一条消息才可能连带减轻 KV 和常驻压力。远程 API 上，同样的缩短主要影响输入 token、费用和延迟，不能说成所有部署的内存都因此下降。库存不受某一次请求的窗口限制，也不等于机器可以无限放得下，更不等于一段概要就能无损还原原文。派生写法可以紧凑；要回到当时的话，仍靠指向还在的原始档案。用户删掉的原文不再是可召回的档案；autoDream 改的是索引、关键记忆和概要，不是把已删除的原文写回去。

第一篇文章用作者自己的本地测量说明：上下文变长会明显抬高已加载模型的内存分配。那些数字属于文章自述，本仓库没有复现，也不收成 agile-agent 的阈值。

表示法可以另作探索：一种类似 AOCI-CODE 的、让模型来读的紧凑语义写法，用来表达事实、实体、关系、变化和来源指针，并保住否定、时间、范围、不确定和更正。这是类比，不是规定语法，也不保证 token 一定变少。是否可读，要看目标模型的分词器和它能否凭来源回到仍在的原文。

## 示意：一次更正，以及下一条短消息

下面是虚构例子，不是测量，也不是要落地的格式或配额。

某会话里，用户先说工号是 W-100，后来说那是错的，工号是 W-5518，并且希望回答使用中文。

- 原始档案留下这两轮，不因为后来窗口变短而改写。
- autoDream 得到机会后，可以自己决定：给关键记忆写下「工号是 W-5518，早先的 W-100 已更正」；在索引里标出更正所在的那一轮；把概要写成仍然完整的一版，里面有语言偏好，也有这次更正。它也可以判定索引不用动。
- 库存里的那版概要就这样留着。
- 下一次请求如果上下文很短，这条消息里只引用概要中与当前问题相称的一小段，例如更正后的工号。这一小段可以随当时的上下文长度和部署环境再长一点或再短一点。被引用的是选择，不是把库存概要换成这几行。

若模型换一种紧凑写法来表达同一选择，那也只是这次引用的表示，同样不覆盖库存全文。

## 和现有四层的关系

设计规格里的四层见 [memory-runtime 设计第 3 节](../superpowers/specs/2026-10-21-memory-runtime-design.md)。代码没有名为 L0–L3 的枚举，职责是对得上的。接口和运维细节见 [api.md](api.md) 与 [operations.md](operations.md)。

- **L0** 是这一条消息里的热上下文，由当次组装而成，不是库存。
- **L1** 是关键记忆，**L2** 是索引。autoDream 若改动，改的是这两层和由它们形成的概要。
- **L3** 是原始档案。整理不把档案和派生结果当成同一份东西。

升温和降温改变的是激活和这一次用多少，不是把唯一的历史从一层搬到另一层。

**已经落地、但还不是 autoDream。** `ContextAssembler` 按调用组装消息：固定前缀、概要、关系、窗口外的召回资料、本会话最近的完整轮次、当前问题。上下文预算默认开（未配置窗口时按 32768 估算，输出预留 4096，估算系数 1.3）。召回资料只在命中落在近期窗口之外时占用历史预算的一部分（默认最多 25%、最多 5 条）。这一层不是本进程里的 KV 条目。会话、消息、执行和工具记录写在 MySQL，默认不因变旧而删除；删除会话是软删除。原文压缩默认关。原文切块在轮次完成后进行，检索默认开，命中后放进提示词的是该轮原文；轮次记录默认不生成，生成了也只作检索索引。`memory_items` 的写入来自可选的闲置判断（默认关）、用户更正、遗忘和恢复。当前 main 没有把判断结果写成关系的生产写入路径。现有后台任务是间隔扫描或闲置入队：清理、按保留期清除来源已删除的派生行、衰减停用、可选的记录或判断。用户删除或遗忘的条目会留下，并且不再进入召回。这些都不是模型自己决定要不要改索引、关键记忆和概要。

**还没落地的是 autoDream 本身：** 由模型在后台机会里审查经历并自行取舍，包括决定不改；库存概要保持全文，只在每条消息里按上下文长度和部署环境选择引用多长。没有固定时刻，也没有已测出的效果。

若以后要看它是否有用，可以比较回答质量、错误记忆、来源能否回到仍在的原文、每条消息的输入规模，以及本机运行时的峰值内存和前台延迟。这些是待测问题，不是本文的结论。
