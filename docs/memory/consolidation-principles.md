# 本地部署下的记忆整理：方向与原则

> **状态：作者正在考虑的方向，不是已批准的实现规格，没有排期，也没有承诺现有代码已经这样做。**
> 对照撰写时的 `main`：`b5b39f48acca4ffb78890cdfd9ed7f67e4952938`。下文「已经落地」只描述这棵代码树里能看到的行为，不描述某一台已部署进程的开关。

agile-agent 要服务下面两篇文稿的目标。本次依据的是作者**上传的 HTML 文稿**，不是从公网重新抓取的页面，因此这里不附文章网址，也不把文中的测量写成本仓库已经复现的基准。

- 《Memory Runtime：从 KV Cache 到长期记忆的分层 AI Memory 架构》
- 《Temporal Semantic Runtime v2.0 — A Dual-Path Cognitive Runtime for Embodied Agents》

第一篇把长期记忆从「无限变长的上下文」里拆出来：工作记忆要有预算，重要的事记成带来源指针的语义对象，目录负责导航，原始档案保留发生过的事。压缩应当减少正在使用的上下文，而不是毁掉来源。第二篇把快速反应、安全约束和慢速思考分成同时存在的路径：世界可以很大，送进模型的上下文必须稀疏；思考不应挡住仍需立刻完成的反应。记忆、情节和偏好的积累本身就是一种学习，不必靠不断改模型参数。

作者此刻的原话是：实现时要针对**本地部署**和**内存开销紧张**来优化。首要的是按设定的上下文长度缩减概要；其次可以试一种类似 AOCI-CODE 的、面向模型的紧凑写法来描述摘要；再者不要人为过多干预，让 Agent 自己决定如何整理「索引 / 关键记忆 / 概要」。下面把这三点展开成原则，并写明和当前代码的距离。

## 1. 按本地机器的几种预算来设计

优化对象是一台资源有限的机器，而不是默认拥有超长上下文或大量云端并发。要分开看四种开销，它们不能互相代替：

| 预算 | 指什么 | 和当前服务端的关系 |
| --- | --- | --- |
| 进程内存 | JVM 堆、直接内存、本进程的缓存 | 镜像默认把堆设为 1 GB（`-Xms1024m` / `-Xmx1024m`），这是镜像参数，不是测出来的最低内存 |
| 模型常驻与 KV | 模型权重，以及随上下文变长的 Key/Value 缓存 | 现有对话走租户配置的远程 API。提供方的 KV 不在本进程里，服务端改提示词长度，并不直接缩小提供方机器上的 KV |
| 输入 token 预算 | 这一轮真正放进提示词的窗口 | 已有按模型窗口估算的上下文预算，默认开启 |
| 磁盘档案 | 库里的原文、派生索引、附件文件 | MySQL 保存会话与派生数据；附件在本地目录，另有按修改时间清理的任务 |

只有模型跑在本机时，缩短提示词才可能连带减轻 KV 和常驻压力。远程 API 部署上，同样的缩短主要影响输入 token、费用和延迟，不能说成「所有部署的内存都因此下降」。

第一篇文章用作者自己的本地测量说明：上下文变长会明显抬高已加载模型的内存分配，能跑起较长窗口不等于适合让它一直常驻。那些数字属于文章自述，本仓库没有复现，这里也不把文中的窗口长度收成 agile-agent 的阈值。原则只保留这一点：热上下文是预算，随模型、硬件、并发和当时的内存压力变化，而不是一个写死的、越大越好的窗口。

## 2. 概要跟着上下文长度和本轮剩余空间收缩

这是资源紧张时的第一件事。

概要（用户记忆概要，以及将来为索引和关键记忆准备的总览）的体积要随**已配置的上下文长度**和**这一轮还剩多少提示词预算**变化。它必须给这些东西留位置：系统说明、当前任务、最近对话、预留输出。窗口短的时候，一篇固定很长的概要不应占满输入。

本文不规定比例、条数或 token 上限。取舍标准是：留下的内容仍然有语义、每条仍能指回来源；装不下时少收几条完整事实，或退回更短的总览，而不是从句子中间截断。否定、时间、范围、不确定和更正优先于多堆无关的细节。

**示意（虚构，不是测量，也不是要落地的格式或配额）：** 假定这一轮的窗口大约只能再容纳几条短事实。概要就不再铺开成完整的五段说明，只保留仍会影响回答的完整句子：

- 回答使用中文。范围：该用户。依据：用户陈述。来源：某会话的某一轮。
- 工号不是 W-100；已更正为 W-5518。范围：该用户。依据：用户确认。来源：某会话的某一轮。

若连这两条都放不下，就先不写与当前问题无关的那条，而不是把「工号不是 W-100」切成「工号不是」。

## 3. 试一种面向模型的紧凑写法

其次可以探索一种类似 AOCI-CODE 的写法：用紧凑的语义结构描述摘要，让模型来读，而不是只写成给人看的长文。类比的是「用短结构表达索引」，不是把代码索引的文件格式原样拿来，也不是声称已经有一套语法。

这种写法若值得试，应能表达事实、实体、关系、变化和来源指针，并保住否定、时间、范围、不确定和更正。评的时候看目标模型的分词器是否拆得开、模型能否读懂、能否凭来源指针回到仍可用的原文。字符变少本身不算成功，也不保证 token 一定下降。

这是实验和类比，不是当前实现。本文不给出具体语法。

## 4. 界限之内由 Agent 自己整理

人负责目标、预算和边界：这段上下文有多长、这一轮还剩多少、租户和用户如何隔离、什么叫明确遗忘或删除。在这些界限里，索引、关键记忆和概要如何增量重组、合并、去重、提升、降温、重写总览，由 Agent 自己取舍。

不把「每条都等人工点头」或「先全部停在待审影子区」当作本方向的要求。作者明确不希望人为过多干预这个过程。

下面这些仍然用确定的规则执行，不交给模型临场放宽：

- 超出预算就停止继续塞进提示词或停止这一轮后台写入。
- 来源指针和访问隔离保持有效。个人记忆停在租户和用户边界内，不把别人的记忆混进来。
- 用户已经遗忘或删除的内容，整理过程不得悄悄恢复，也不得把推断写成用户已确认。
- 档案保留服从用户的删除指示。不能为了「以后也许用得上」把用户要求去掉的内容继续留在可召回路径上。

## 5. 整理放在慢路径上，并且可以找回原文

这和两篇文章是对齐的。Memory Runtime 的四层是职责，不是四套互相搬迁的库：L0 是此刻的热上下文，L1 是值得记住的语义，L2 是知道去哪里找的目录，L3 是当时发生了什么。升温和降温改变的是激活、排序和粒度；历史事实仍以 L3 为准。Temporal Semantic Runtime 则要求慢的思考不要挡住安全约束和快速反应。

因此，重的整理离开前台这一轮的回答路径。若以后出现独立的安全路径或实时反应路径，整理同样不插进那两条路径。工作量按增量、有上限；何时跑由配置决定。本文不批准固定时刻，也不要求每个周期把全部历史重扫一遍。讨论里出现过「离线再整理一轮」的想法；那只是灵感，不是对任何外部产品内部实现的核实，也不是已经排上的日程。

派生表示可以有损。概要或紧凑索引变短，不能证明单靠这段文字就能无损还原原文。找回依赖指向**仍然可用的 L3** 的来源指针。来源已经按用户意图删除时，指针不得把内容重新召回。

## 6. 以后要验证什么

下面是建议测量的问题，不是本文件宣布的结果。预算变小也不等于已经证明所有部署形态的内存都下降了。

- 回答质量和关键事实召回
- 矛盾与错误记忆（含把推断当成确认、把已遗忘内容说回来）
- 来源能否回到仍保留的原文
- 输入 token
- 仅当模型跑在本机时：峰值内存，以及运行时报告的 KV 或等价占用
- 前台延迟，以及后台整理的耗时和费用

第一篇文章自己列出的对照也是同一类问题：整段历史直接进提示词，对比有预算的热上下文加关键记忆、检索片段和来源指针。那个对照尚未在本仓库执行。

## 7. 当前 main 已经做了什么

设计规格里的四层见 [memory-runtime 设计第 3 节](../superpowers/specs/2026-10-21-memory-runtime-design.md)。代码没有名为 L0–L3 的枚举，职责是对得上的。接口和运维细节见 [api.md](api.md) 与 [operations.md](operations.md)。

**L0，当前上下文。** `ContextAssembler` 按调用组装消息：固定前缀、概要、关系、窗口外的召回资料、本会话最近的完整轮次、当前问题。上下文预算默认开（未配置窗口时按 32768 估算，输出预留 4096，估算系数 1.3）。召回资料只在命中落在近期窗口之外时占用历史预算的一部分（默认最多 25%、最多 5 条）。这一层不是本进程里的 KV 条目；远程 API 的 KV 由提供方管理。

**L3，原始档案。** 会话、消息、执行和工具记录写在 MySQL，范围是租户、用户和会话，默认不因变旧而删除。删除会话是软删除。原文压缩（温层 / 冷层）默认关，它只改变同一层原文的存法。

**L2，索引。** 轮次完成后会为原文切块（`memory_chunks`），检索默认开：编号精确匹配、全文和尚未建索引的最近轮次。命中后放进提示词的是该轮原文，不是索引正文。轮次记录（`memory_summaries`）默认不生成；生成了也只作检索索引。没有向量检索、查询改写或重排。

**L1，关键记忆。** `memory_items` 可以挂在会话上，也可以是用户级。写入来自可选的闲置判断（`app.memory.judgement.enabled` 默认关）、用户更正、遗忘和恢复。用户概要由有效的用户级条目渲染成「偏好 / 身份 / 进行中 / 约束 / 其他」，默认上限约 800 个估算 token；超出时从正文前部截断。跨会话开关默认关，关闭时不读取概要。一跳关系的读取和「删除概要时整图失效」已经接上；当前 main 没有把判断结果写成关系的生产写入路径。召回排序会按最近召回时间衰减；非用户陈述的条目过久未召回会变为不激活，默认约 180 天、每小时扫一批，这不删除行。用户陈述和用户确认不会因此变为不激活。

**还不是本文说的整理。** 现有后台任务（清理扫描、派生索引清除、衰减停用、闲置后的记录或判断）是间隔扫描或闲置入队，不是 Agent 在预算内自行重组索引、关键记忆和概要。清除只处理来源已删除且过了保留期的派生行；用户删除和遗忘的条目会留下，并且不再进入召回。这些规则应继续守住，但它们还不构成第 4 节的自主整理。

## 非目标与还没定的问题

本文不改代码，不新增定时任务，也不把具身运行时的安全路径、电机控制或世界模型拉进当前服务端。向量库、组织级共享记忆、把跨会话默认打开，都不在这个方向里。

还没定、因此不能写成规格的有：紧凑写法如何验收才算模型读得懂；概要预算怎样从配置窗口和本轮剩余空间算出来；后台整理的间隔和批量由哪项配置控制。这些都可以以后再定，本文不给数值。
